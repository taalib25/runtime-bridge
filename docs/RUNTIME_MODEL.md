# Runtime Model

## Product Concepts

| Term | Definition |
|------|-----------|
| **Workspace** | Product-level grouping owned by a user or team. Maps 1:1 to a Helm release + k8s namespace. |
| **Instance** | An isolated Hermes runtime environment managed by the bridge. |
| **Profile** | Hermes-native profile inside an instance. Same-customer only — different customers must never share a Hermes data directory. |
| **Agent Template** | Reusable SOUL.md / config / model / integration preset stored as a k8s ConfigMap in the bridge namespace. Applied via Helm upgrade with `OverwriteConfig: true`. |

Product language uses **instance**. Internal runtime code uses the Kubernetes terms
(pod, deployment, PVC, secret, service).

## V1 Model — Standard Plan

One customer instance maps to:

```
Namespace:    <workspace-id>          (e.g. tenant-290f0b64)
Deployment:   <workspace-id>          (1 pod, Recreate strategy)
Pod:          1 replica               (Hermes runtime image)
PVC (state):  <workspace-id>-state    (HERMES_HOME at /home/hermeswebui/.hermes)
PVC (ws):     <workspace-id>-workspace (/workspace subdir)
Secret:       <workspace-id>-secrets  (bridge-owned, API keys + integration tokens)
Service:      <workspace-id>          (ClusterIP, port 8787)
IngressRoute: <workspace-id>          (HTTPS via Traefik, workspace.hermeshq.net)
```

## Team / Multi-Profile Mode

For team plans where multiple Hermes profiles share one instance:

- One Hermes instance (Deployment / Pod)
- One shared PVC (`HERMES_HOME`)
- Hermes profiles configured inside the same customer boundary
- Each profile gets its own sub-directory under `HERMES_HOME/profiles/`

Different customers **must not** share one Hermes data directory.

## Enterprise Model

Enterprise instances are deployed as:

1. Same cluster, dedicated namespace (default enterprise)
2. Same cluster, dedicated node pool (`nodeSelector` / `tolerations` in WorkspaceSpec)
3. Dedicated K3s cluster (separate bridge deployment)
4. Standalone VM + Docker Compose (special case — see `prod-hermes-docker-image/` in `_archive/`)

Default enterprise path uses K3s + Helm + bridge unless a customer explicitly
contracts for a standalone VM deployment.

## Secret Ownership

The bridge owns workspace secrets directly. Helm **never writes** secret values.

```
Secret values   → bridge-patched k8s Secret (bridge creates/updates via k8s API)
Secret env refs → Helm values["extraSecretKeys"] (env var name → secret data key)
Plain env config → Helm values["extraEnv"]  (TELEGRAM_ALLOWED_USERS, etc.)
```

This split is intentional. See `bridge/providers.go` and `bridge/integrations.go`.

## Workspace ID Format

```
tenant-{8 random hex chars}    e.g. tenant-290f0b64
```

The same ID is used as: Helm release name, Kubernetes namespace, subdomain prefix.
Generated by the backend, stored in the product database, passed to the bridge on
every create/update call.
